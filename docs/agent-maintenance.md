# Agent maintenance and research resumption

Agent and model upgrades change how work is executed. They do not change a
physical claim, its acceptance criteria, or an existing owner's authorization.
The numerical library remains independent of any model provider.

## Locate authority before choosing a workflow

| Task | Controlling records | Completion boundary |
| --- | --- | --- |
| Read-only status or review | Current task request, canonical state, latest linked handoff | Explain the checked state; do not open an intake or calculation. |
| Infrastructure or instruction maintenance | Requested files and behavior, repository instructions, compatibility contract | Implement and validate the authorized change; research decisions remain separate. |
| One scientific gate | Frozen contract and its recorded bounded autonomy window | Complete the listed routine work and return at the first declared stop or outcome. |
| Autonomous research | Exact authorized mission, pinned framework, state and control-plane receipts | Follow delegated transitions only; preserve a terminal campaign when maintenance begins. |

An explicit instruction in the current task controls routine implementation
choices over a generic skill default. Reuse authorization already given for the
same scope; do not ask again merely because another skill mentions approval.
Keep scientific investment, frozen-contract changes, Git actions and disclosure
within their separately recorded authority. If an actual decision is missing,
finish the authorized preparation first, identify the exact controlling rule,
and present a concrete decision with its evidence.

The A-E menu belongs to an owner scientific handoff or the next eligible
portfolio decision. A status answer, maintenance report, or authorized routine
step does not manufacture another pending scientific decision. Preserve the
handoff requirements in the research-gate workflow when a real owner gate is
reached.

## Deliver authorized public changes

`AGENTS.md` records standing owner authorization to commit and push scoped,
owner-requested work in this public repository. After relevant local checks
and public-content review pass, inspect every outgoing commit, verify the
existing `origin` destination and intended branch, and use a normal
fast-forward push. Do not include unrelated work or repeat the permission
question for that routine delivery. Verify the remote commit and report the
actual CI result; a successful push alone does not establish passing CI.

Honor any narrower instruction for the current task. This permission does not
authorize merging, releases, branch deletion, force pushes or history rewrites,
changing the remote destination, private export or scientific disclosure. It
does not expand a frozen research window or autonomous mission, or authorize
changing its pinned framework. Those actions retain their separate authority.

## Keep navigation distinct from historical evidence

A private repository needs its own short `AGENTS.md`; instructions in a sibling
public checkout are not an automatic private-workspace entry point. Link the
applicable framework pin, current project state, latest owner handoff, decision
ledger and reviewed-knowledge index. Dedicated campaigns retain their own
instructions and immutable pins.

Current state and the latest explicitly superseding handoff determine present
status. A README proposal, earlier review packet, or conversation summary can
be historical. Navigation should point to those controlling records rather
than maintain another independent statement of scientific authority. Generated
indexes should include source hashes and exact line locators, stay visibly
derived, and be regenerated after the source changes. They never grant review
status or execution permission.

When claim-level navigation is useful, the opt-in
[claim/evidence index](claim-evidence-index.md) can check pinned references and
flag affected dependencies. It is primarily agent-facing; PDF remains the
human review format when needed. Adopting the utility does not migrate frozen
framework pins, rewrite historical reviews, or create another owner gate.

Load the relevant records for the current operation. Preserve full histories,
but retrieve applicable stable knowledge IDs and primary evidence instead of
repeatedly loading every closed project. Read controlling sections and their
prerequisites once per relevant revision; revisit them when their version or
task boundary changes. Skill entry points identify shared controls and
phase-specific links; execution does not require rereading intake or PDF
guidance unless that phase is relevant. This changes retrieval, not the scientific contract.

Presentation changes apply prospectively: routine reports use a short status
summary, with research-process figures and separate progress PDFs only on an
explicit owner request. Preserve historical snapshots, reviewed PDFs and
frozen manifests. Keep canonical research state current and link it for
resumption instead of treating an old diagram as live state. A reporting
preference does not migrate a framework pin or authorize scientific work.

When reviewing instruction changes, walk through representative status,
targeted-review, documentation-fix, and scientific-gate requests. Check which
records they load, what work they authorize, and where they finish. Link and
metadata checks establish discoverability, not agent judgment or performance.
Keep acceptance criteria, authorization, privacy and transition checks; avoid
requiring the same policy prose in every entry point and reference.

## Choose checks that can establish the intended behavior

| Change | Required local checks |
| --- | --- |
| Documentation, links or skill wording only | Inspect the diff and references; run affected onboarding, skill or policy checks and `git diff --check`. |
| Campaign schema, validator or orchestration | Run schema and positive/adverse transition, authorization, budget and artifact tests; then the full suite and documented soft-wall smoke verifier once. |
| Numerical method, observable or scientific result | Run the frozen claim-specific controls, relevant public commands, full regression suite and synchronized scientific records. |
| Packaging, dependencies or public interfaces | Exercise the affected installed-package behavior plus the full suite and smoke verifier. |

Full default CI remains required for a public integration. During pre-1.0
development, this means the complete Python 3.11 scientific suite, historical
audit, package smoke check, and macOS wheel-portability check. The wider Python
and operating-system matrix is an explicit manual `full_compatibility` run;
use it before Version 1.0 or a broader compatibility claim, as described in the
[runtime policy](version-0.5-compatibility-policy.md#supported-runtime-and-platforms).
Do not multiply routine jobs across other Python versions merely because they
remain in the package's allowed installation range. Once the required checks
pass, rerun them only after a relevant change or new evidence of a problem.
Do not weaken a scientific check to save time.

Report mocked orchestration tests, saved-data replay, actual integrations,
independent numerical methods and scientific acceptance separately. Passing
routing tests cannot qualify the solver they mock. After a changed numerical
representation or tolerance, explicitly identify which fitted or derived
inputs need requalification under the same frozen physical conditions; do not
silently reuse a stale fitted input or expand an exhausted repair window.

## Record execution, not just requested roles

Before delegating, verify the tools and model/effort choices exposed by the
actual platform. A configuration flag or valid mission string does not prove
that a specialist was started. Codex effort labels and API-supported settings
must be checked in their respective deployment; do not silently map one to the
other or replace a pinned model because a newer name exists.

For each executed role, preserve an artifact receipt with the requested and
actually reported model/effort, platform/runtime version when available, input
snapshot hashes, instruction revisions, produced artifacts and how they were
checked. Mark unavailable metadata as unavailable. Model substitutions require
the authority specified by the mission; they cannot rewrite its frozen bytes.
Include receipts in the existing artifact manifest when the mission requires
them, without changing historical provenance or claiming stronger independence.

Use a fresh verifier context with the immutable common inputs needed for its
check. Restrict its file/search scope to those inputs until it seals its own
result, then compare with the executor. Separate roles alone do not establish
independent methods or human review. Keep one canonical writer.

## Maintain first, resume from the recorded checkpoint

1. Confirm the affected tasks are idle or explicitly held. Record current
   checkpoints and protect unrelated changes, frozen records and framework pins.
2. Review existing unintegrated generic changes before implementing another
   version of the same fix. Keep private evidence out of public patches.
3. Complete the scoped maintenance and validation. Report changed files,
   checks, compatibility limits and whether a local commit exists.
4. Notify held tasks of completion only when requested or authorized. Have
   each task reread its current state and applicable instructions before work.
5. Resume only the next action actually authorized by its owner. Maintenance
   completion is not approval of a proposed repair or a new campaign. Do not
   rerun completed calculations simply because the agent model changed.

An immutable terminal campaign stays terminal. A future mission or an explicitly
authorized continuation uses a prospective contract and a reviewed framework
pin or separately recorded overlay. Never update the old campaign's framework,
mission hash, evidence or human decisions in place to make it appear migrated.
